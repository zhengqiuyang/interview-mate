# Agent 技能市场：把工具和专家人设做成可分享的数据

> 系列第 4 篇。前两篇讲完了工具协议和会诊，这套 Agent 系统的最后一跃是：让用户自己定义工具和专家——不写代码。
> 仓库：https://github.com/zhengqiuyang/interview-mate

## 一、思路：从「功能」到「数据」

技能市场之前，Agent 的工具是写死在 `TOOLS` 对象里的 10 个函数，专家是 `PANEL` 数组里的 3 条配置。要做扩展性，思路不是写插件系统，而是更彻底的一步：**把这些硬编码的东西降格为数据，让用户数据与内置定义平权**。

```js
// 工具执行时的查找顺序：内置 TOOLS → 自定义 HTTP 工具
if (TOOLS[call.name]) return await TOOLS[call.name](call.args || {});
const t = S.customTools.find((x) => x.name === call.name);
// ……按 URL 模板发请求
```

模型根本不知道一个工具是内置的还是用户定义的——提示词里两者并列声明，协议层面完全一致。这是整个技能市场最重要的一条边界。

## 二、自定义 HTTP 工具：URL 模板就够了

用户最常见的诉求是「让 Agent 能查我们公司的内网接口 / 某个公开 API」。为此设计的工具定义只有四个字段：

```js
{
  name: 'github_search',           // 模型调用用的标识
  argsHint: 'query',               // 参数名，与 URL 模板对应
  description: '搜索 GitHub 仓库……', // 给模型看的用途说明
  urlTemplate: 'https://api.github.com/search/repositories?q={{query}}&per_page=5',
}
```

执行时代码做参数插值，然后把请求发给**本机服务的代理端点**：

```js
let url = t.urlTemplate;
for (const [k, v] of Object.entries(call.args || {})) {
  url = url.split(`{{${k}}}`).join(encodeURIComponent(String(v)));
}
const res = await fetch('/api/tools/http', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ url }),
});
```

为什么要绕道本机服务端而不是浏览器直连？**CORS**。绝大多数 API 不给浏览器跨域调用，但服务端之间没有同源策略。服务端代理的实现只有一个约束值得说：`new URL()` 解析后校验协议必须是 http/https——防 `file://` 和各种奇怪 scheme，加上 12 秒超时、返回截断 3000 字符。个人工具的安全模型做到这个程度刚好：防误伤，不装企业级。

`description` 字段是被低估的关键——它就是给模型的「工具说明书」，写得越具体（什么场景调、返回什么），模型调用得越准。技能市场的新建表单里这个字段的提示文案是「给模型看，越清楚越容易被正确调用」。

## 三、自定义专家：一段人设走天下

上一篇讲过，自定义专家通过 `personaText` 直通系统提示词。用户在表单里填三样东西：名字、图标（一个 emoji）、任务指令（这位专家做什么、怎么输出）。保存后自动出现在会诊面板的候选列表里，⭐标记区分于内置专家。

任务指令的写作门槛比看起来低——官方技能包里有现成范例可抄，比如「薪资谈判教练」的指令：

```text
你是资深薪资谈判顾问。先了解我的情况（可用 my_stats、get_resume），
然后帮我评估目标薪资区间、给出谈判开场话术、锚定策略、以及应对 HR 压价的
3 套回应。结合我的技术栈与市场行情给具体数字区间。
```

结构就是：**身份 → 数据获取指令 → 输出清单**。用户写不出好指令时，还有导入功能直接用别人调好的。

## 四、分享：技能即 JSON

工具和专家存 localStorage，导出成一个 JSON：

```json
{
  "app": "interview-mate-skills",
  "tools": [ { "name": "github_search", "urlTemplate": "……", "description": "……" } ],
  "experts": [ { "name": "薪资谈判教练", "task": "……", "icon": "💰" } ]
}
```

导入时做三重校验：`app` 字段验身份；工具名查重（与内置和已有自定义都不冲突才收）；人设指令必填。校验失败的条目跳过、成功的照收——部分成功优于整体失败。

没有账号体系、没有后端存储，「市场」的本质是**文件交换**。这对个人工具是诚实的答案：技能的传播成本就是发一个文件。

## 五、官方技能包：冷启动的内容运营

自定义能力再强，空白的表单也劝退新用户。所以内置了 5 个官方技能包，一键安装：

| 技能包 | 类型 | 一句话 |
| --- | --- | --- |
| 💰 薪资谈判教练 | 专家 | offer 评估、锚定策略、应对压价 |
| 🇬🇧 English Interviewer | 专家 | 英文技术面模拟与表达纠偏 |
| 🏛️ 首席架构师评委 | 专家 | 以晋升答辩标准出系统设计题链 |
| 🐙 GitHub 仓库情报 | 工具 | Agent 能搜 GitHub 做技术选型调研 |
| 🟠 HN 技术情报 | 工具 | Agent 能搜 Hacker News 看业界口碑 |

安装即把定义复制进用户的自定义列表（标记来源），可删可改。它们同时是**教学素材**——用户看完官方人设怎么写，自己写就有谱了。

## 六、边界与教训

- **不做任意代码执行**。自定义工具只有 HTTP 一种执行方式，永远不提供「跑一段用户 JS」——那是一条安全不归路。
- **工具数量上限 8 个注入提示词**。工具太多模型选择准确率下降，宁缺毋滥。
- **人设质量参差是常态**。自定义专家的效果高度依赖指令写作水平，解法不是收紧校验而是提供范例。

## 七、小结

技能市场的完整链路：**硬编码降格为数据 → HTTP 工具模板化 → 服务端代理绕 CORS → JSON 文件做分享 → 官方包做冷启动**。没有一行插件 API，但扩展性一步到位。
