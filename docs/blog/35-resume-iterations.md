# 同一个功能的三轮迭代：简历工坊从文本框到原生文档预览的产品教训

> 系列第 35 篇（C 线·产品与算法设计之三）。简历工坊是这个项目迭代次数最多的模块——三轮重做，每轮都是被用户反馈推翻的。复盘这三轮，比讲任何成功设计都有料。
> 仓库：https://github.com/zhengqiuyang/interview-mate

## 第一轮：能用的文本框

v0.1 的简历功能就一个 textarea + 一个「诊断」按钮。粘贴简历文本、粘贴 JD、点按钮出报告。

从工程视角它无懈可击：数据流最短、无解析风险、AI 全权处理。但它的产品体验是**把文档工作流降格成了填表单**——用户面对的是一个空白输入框，而他的资产是一个 .pdf 文件。

教训一：**「AI 能处理纯文本」不等于「用户应该自己变成纯文本」**。输入形态的鸿沟是第一道流失点。

## 第二轮：解析文本，但仍是我以为的展示

v0.15-0.16 加了上传解析（PDF 用 pdf.js 提文本、DOCX 零依赖解包），并做了「结构化展示」：AI 把解析文本拆成姓名/头衔/技能/分节，渲染成漂亮的文档卡片。简历库支持多版本管理。

我自己挺满意——上传即解析、解析即展示、展示可编辑。然后用户说了一句话：

> 「我想要的是**原生的那种 Word 或者 PDF 文档展示**，不是你提取文字出来。」

这句话推翻了我对「展示」的全部理解。我以为用户要的是「信息被组织好」，用户要的是「**我的简历原封不动地出现在屏幕上**」——那是我打印出来交给 HR 的同一份文件，熟悉的排版、自己调过的间距。结构化卡片再漂亮，也是「系统对我的简历的转述」，不是我的简历。

教训二：**「转述」和「原件」之间隔着信任**。文档类产品里，原件展示不是锦上添花，是用户确认「系统真的拿到了我的东西」的仪式。

## 第三轮：原生预览 + 双视图

v0.17 的最终形态：

```
上传 → 文件本体存服务端（data/files）→ 展示区分两个标签
  ├─ 📄 原文预览：PDF 用 iframe 内嵌浏览器原生查看器（带页面/缩放）
  │              DOCX 用 docx-preview 渲染成带页面的 Word 视图
  └─ 🧩 结构化：AI 智能解析的文档卡片（供 AI 功能挂载）
```

关键决定：**两个标签页并存，而不是用原生预览替换结构化**。因为它们服务不同时刻的用户：刚上传时看原文（确认与信任），开始用 AI 功能时切结构化（编辑、诊断、润色都作用在结构化侧）。**原文是心理账户，结构化是工作账户**。

技术上的三个坑也值得记录：

1. **文件必须落服务端**。localStorage 塞不下几 MB 的 PDF，浏览器也无权把本地文件路径长期持有——`data/files/` + 上传接口（后缀白名单、路径防穿越、20MB 上限）是绕不开的基建
2. **DOCX 渲染库的完整性依赖**：手搓的测试 docx（只有一个 document.xml 的极简 zip）docx-preview 渲染不出来——真实 Word 文件带全套 OOXML 部件。**测试样本必须用真实工具产出**，这是二进制格式调试的通用律
3. **提取文本仍然保留**：AI 诊断需要纯文本，「看原件」和「喂模型」是两条并行数据流，不该为了一个砍另一个

## 三轮的元教训

把三轮拉通看，迭代方向是一条清晰的线：**每一轮都在缩短「用户的资产」和「系统的呈现」之间的转换层数**。

```
第一轮：用户自己转换（pdf → 文字 → 粘贴）
第二轮：系统转换但换形态（pdf → 文字 → 结构化卡片）
第三轮：原件直出 + 转换并行（pdf → 原生预览 ∥ 文字 → 结构化）
```

而驱动每一步的都不是我的设计想象力，是用户的原话。第二轮做完时我确信「结构化展示」就是终点——如果没有那句「我要原生的展示」，这个产品会停在离正确答案一步的地方。

**做产品最难的不是听懂用户说什么，是意识到自己刚才引以为傲的那版答案，只是问题的一半。**
