# 求职闭环的产品设计：五段状态机怎么把五个工具串成一个系统

> 系列第 31 篇（C 线·产品与算法设计之二）。工具型产品最怕「功能齐全但各自为战」。这篇讲 InterviewMate 怎么用一个投递状态机，把岗位雷达、简历工坊、模拟面试、复盘画像串成闭环。
> 仓库：https://github.com/zhengqiuyang/interview-mate

## 一、先诊断：五个工具，五种孤岛

没有投递看板之前的状态：岗位雷达攒了一堆 JD、简历工坊存了三个版本、模拟面试打了五场、错题本记了二十题——**它们之间没有任何连接**。用户的真实流程是连续的（看到岗位→改简历→面试→复盘→跟进），产品却是五个断点。

串联的钥匙是意识到：**求职的自然主键不是「知识」也不是「简历」，是「一次投递」**。围绕它建状态机，其他模块全变成状态流转上的挂件。

## 二、状态机本体

```
已投递 → 约面/筛选 → 一面 → 二面 → 三面/终面 → HR 面 → Offer
                     ↓ 任一环节
                   挂了 / 搁置
```

数据模型：

```js
{
  id, company, position, channel, salary,
  date, interviewDate, resumeId, jdUrl, note,
  status: 'applied' | 'screening' | 'interview1' | ... | 'offer' | 'rejected' | 'paused',
  history: [{ status, date, note }],   // 状态流水，不可变审计日志
}
```

两个关键设计：

**NEXT 映射表**定义合法流转：`applied → screening → interview1 → ...→ offer`。看板卡片上的「→」按钮一次推进一格——**不提供跳级**。真实求职里确实有「一面直接到 HR 面」，但状态机的价值在于规范数据（转化率统计的分母不能乱），例外让用户通过编辑面板直接改 status 兜底。

**history 只追加不修改**。每次流转 push 一条 `{status, date}`，界面渲染成时间线。它同时是审计日志（「我三面是哪天面的」）和漏斗统计的数据源（投递→约面率 = screening 及以后的比例）。

## 三、模块间的四个挂点

状态机本身只是台账，闭环感来自其他模块「挂在」状态上：

**挂点一：岗位雷达 → 投递**。雷达汇集的岗位一键批量导入为「已投递」记录（带 JD 链接和薪资）。发现和记录之间原本隔着手动誊抄，现在是勾选框。

**挂点二：interviewDate → 全局提醒**。记录上设了面试日期的投递，触发三处联动：看板顶部横幅（「⏰ 即将面试：字节跳动（3 天后）」）+ 卡片倒计时徽章 + **每日简报点名**。提醒功能单独做没人看，嵌在用户每天必看的简报里才有用。

**挂点三：resumeId → 简历版本追溯**。每条投递记录关联「当时用的哪个简历版本」。三个版本简历投了三十家公司，事后复盘「哪个版本约面率高」就有了数据基础。

**挂点四：`my_applications()` → Agent 工具**。投递数据开放给 AI Agent：直接问「分析我的投递转化率，该重点跟进谁」，Agent 调工具拿到全部记录和统计。**数据结构的终点是成为 Agent 的上下文**。

## 四、转化漏斗：四行统计的克制

```js
const active = apps.filter((a) => !['offer', 'rejected', 'paused'].includes(a.status));
const offers = apps.filter((a) => a.status === 'offer');
const screened = apps.filter((a) => a.status !== 'applied');
约面推进率 = screened.length / apps.length
```

只做四个数字：总投递、进行中、Offer、约面率。做完整的漏斗图（投递→约面→一面→…→offer 的逐级转化）技术上不难，**克制的原因是样本量**——个人求职一季也就投三五十家，逐级漏斗的每一格都是个位数，画出来只有焦虑没有洞察。四格统计是「样本量友好」的最大信息量。

## 五、产品教训：状态机是用户的心理外挂

上线后最有价值的反馈：用户说填完投递记录、推进一格的时候，「求职的失控感」明显下降了。

复盘这事的机制：求职最大的心理消耗是**不确定性堆叠**（投了多少？哪些该跟进？面试在哪天？全在脑子里）。状态机把这些从工作记忆卸载到外部系统——和 GTD 的原理同源，但比待办清单多了**不可逆的时间线**（挂了的记录不删，留在那成为「已完成的努力」的证据）。工具产品的深水区功能，往往是在替用户管理情绪而不是管理信息。

## 六、小结

| 设计 | 一句话 |
| --- | --- |
| 主键选择 | 以「一次投递」为主键，其他模块变挂件 |
| NEXT 表 | 状态流转白名单，统计的分母不乱 |
| history 流水 | 只追加的时间线 = 审计 + 漏斗数据源 |
| 四格统计 | 样本量决定克制 |
| 心理价值 | 卸载不确定性比管理信息更深一层 |
